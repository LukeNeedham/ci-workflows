# The README standard

Every app in [`apps.json`](../apps.json) has a `README.md` at its repo root in the same layout, so any app can be
picked up and understood the same way. The layout lives **here**; the content lives **in each app**, in a
`readme.yml` at its repo root.

## How it works

1. The app has **`readme.yml`**, written by hand ([skeleton](readme-template.yml)): the name, tagline, description,
   the license, and a few optional parts. **Only what is specific to the app.**
2. [`scripts/generate_readme.py`](../scripts/generate_readme.py) renders **`README.md`** from it in the standard
   layout. **What every app shares comes from the script, and from the project itself:**
   - the **minimum Android version**, read from `minSdk` in `app/build.gradle.kts` (and the platform to install, from
     `compileSdk`), so it can never be out of date, and the build fails if it cannot be read;
   - the icon, the screenshots (the PNGs of `docs/screenshots/`), the install step, the generic developer setup (the
     requirements, the clone, build and test commands, CI), "Contributing" and the links;
   - **the architecture is not described in the README**: it is the same in every app and enforced by the shared
     conventions of this repo ([pages.md](pages.md), [app-conventions.md](app-conventions.md), the Claude skill), so the
     generated developer section only points to them.
3. The `readme` job of [`android_pr.yml`](../.github/workflows/android_pr.yml), whose steps are the composite action
   [`.github/actions/readme`](../.github/actions/readme/action.yml), runs the script on every PR, like the
   [app icon](app-icon.md) job, and **commits `README.md` to the PR branch** when it differs.

So: **edit `readme.yml`, never `README.md`** (it carries a "generated" comment and is overwritten). The content is
handwritten; only the layout is generated. When the app changes in a way a reader would notice (what it does, how it
is installed, a setup step), update `readme.yml` in the same PR.

To change the layout for every app, change the script here: the next PR in each app gets a regenerated README.

## The layout

In this order (the title block and the sections are always there, so they cannot be forgotten):

1. The app's icon (the root `app-icon.png`, [generated by CI](app-icon.md)), its name as the one `#` heading and the tagline.
2. `## Description`: includes the highlights of what the app does, instead of a feature list
3. `## Screenshots`: one image per PNG in `docs/screenshots/`, which [CI renders from the app's screenshot package](screenshots.md). **Every app has at least one: there is no option to go without**
4. `## Getting started as a user`: install from the app hub (AppHub) or the Releases page, then the app's own
   `user.steps`, then **the minimum Android version, read from the project**
5. `## Getting started as a developer`: the **generic** setup (requirements with the platform of the project, clone,
   build and test commands, CI, and a pointer to the shared architecture and conventions), then **`developer.notes`:
   only what is specific to this app** (a secret, a local setup step, a quirk)
6. Any `sections` of the app (Privacy, Roadmap, Credits, Known issues), as `## <title>`
7. `## Contributing`
8. `## License`: `license`, with a `LICENSE` file at the repo root; "All rights reserved" if the app is not open source (then no `LICENSE` link is rendered)

## Fields of readme.yml

| Field | Required | Meaning |
|---|---|---|
| `name`, `tagline` | yes | The app's name and one line on what it does |
| `description` | yes | What it is and who it is for, with a few highlights of what it can be used for; a paragraph or two. There is no feature list and no limits section |
| `user.install` | no | Replaces the default first step (install from AppHub or the Releases page), for an app that is not installed that way |
| `user.steps` | no | Steps after installing, such as first-run steps |
| `developer.notes` | no | Only what is specific to developing this app (a secret, a local setup step, a quirk). The generic setup is generated, and the architecture is shared by all apps, so neither belongs here |
| `sections` | no | Extra sections: a list of `title` and `body` |
| `license` | yes | The license name |

Unknown fields are an error, so a typo does not silently drop content. Keep it accurate over long.

## Running it yourself

Not needed, since CI does it, but to see the result before pushing (from the app's repo root):

```
pip install pyyaml
git clone --depth 1 https://github.com/LukeNeedham/ci-workflows /tmp/ci-workflows
python3 /tmp/ci-workflows/scripts/generate_readme.py .            # writes README.md
python3 /tmp/ci-workflows/scripts/generate_readme.py . --check    # writes nothing, exits 1 if README.md is out of date
```

## Rollout and reporting

- An app's **first `readme.yml` PR also brings it in line with the rest of the standard**: its pages renamed and split as
  `XPage` + `XPageContent` ([pages.md](pages.md#migrating-an-existing-app)), and its `screenshot` package
  ([screenshots.md](screenshots.md)). The README cannot be generated before, since it shows the screenshots.
- An app with **no `readme.yml`** gets a warning in its PR build and keeps its current README until it has one.
  The [sync](sync.md) lists such apps (and invalid `readme.yml`s) in its run summary. It never writes a `readme.yml`.
- The managed `CLAUDE.md` block that the sync gives every app tells Claude to write `readme.yml` once from the
  template when it is missing, and afterwards to edit only it. The skill says the same ([skill.md](skill.md)).
- **Forks:** a PR from a fork cannot be committed to, so there the job fails if `README.md` is out of date and says
  to run the script.
